# RAG-Reader：产品分析与实现方案

> 创建日期：2026-10-21
> 状态：方案阶段

---

## 一、问题定义

### 1.1 核心矛盾

个人知识管理面临一个结构性矛盾：

- **输入端**：分散在小红书、知乎、PDF、网页、碎碎念 log 等多个来源，格式各异
- **处理端**：复制粘贴没有意义，但"阅读感想"才是真正有价值的沉淀
- **输出端**：做项目时需要"核心记忆"随时可调用，而不是打开一个阅读器慢慢搜

现有工具要么太重（MediaCrawler 为公开数据批量采集设计，维护成本远超个人需求），要么太轻（纯 RSS 阅读器只做"订阅和打开"，不解决知识沉淀）。

### 1.2 需求拆解

| 需求层次 | 具体描述 | 技术形态 |
|---------|---------|---------|
| **自动同步** | 收藏夹增量同步到本地 | 带登录态的导出器（Playwright 驱动） |
| **静态索引** | 所有积累的原文可搜索 | 本地向量索引 + 全文检索 |
| **动态记忆** | 做项目时 Agent 可调用相关片段 | MCP Server 暴露给 AI 客户端 |
| **感想沉淀** | 阅读时随手写两三句，不整理 | Obsidian frontmatter + 双向链接 |

**关键洞察**：这四层不应该由同一个"阅读器"来承担。把"同步"交给专门的导出器，把"索引"交给 MCP Server，把"感想"留给自己在 Obsidian 里写——各自都有成熟方案，粘合成本远低于改造一个定位错配的工具。

## 二、现有项目分析

### 2.1 MediaCrawler（XHS 模块）

**定位**：自媒体平台公开数据批量采集工具

**技术架构**：
- Playwright 保存登录态 + JS 签名逆向（xsec_token, xsec_source）
- 三种模式：关键词搜索、指定帖子 ID、创作者主页
- IP 代理池、频率控制、stealth.min.js 反反爬
- 核心在 `media_platform/xhs/core.py` + `client.py`

**为什么不适合个人收藏夹同步**：
- 设计目标是"广度采集"（一次配置采集成千上万条公开笔记），不是"增量同步"
- 签名算法逆向成本高，平台一变就挂
- 代理池、反反爬等基础设施对"每天取一杯水"的个人场景是过度工程
- **没有"收藏夹增量同步"模式**——它根本不为这个场景设计

**结论**：MediaCrawler 的"脆弱"不是它做得不好，而是它的强项用在了不需要那么强的地方。收藏夹同步不需要"爬虫"，需要的是"带登录态的、可重入的导出器"。

### 2.2 QMReader（RSS-Reader-consilidation）

**定位**：自托管 RSS 阅读工作台，面向技术内容阅读 + AI 辅助消化

**技术架构**：
- 标准 RSS 解析（rss-parser）+ RSSHub 中转
- 对受保护站点（XHS、知乎）采用 `localOnly` 模式：不爬，只读本地 markdown
- `lib/xhs-kb-sync.js`：本地 markdown 导入器，扫描目录 → 解析正文/图片/元数据 → 转 RSS 条目格式入库
- SQLite 存储 + 双真相收敛（DB 为权威，cache.json 为加速层）
- AI 伴读（文章上下文对话）、双语翻译、乔木风格改写

**`localOnly` 模式的诚实与缺口**：
- 正确做法：把不稳定的部分（XHS 爬取）隔离在核心系统之外
- 真正的缺口：**只定义了"本地 markdown 应该长什么样"，却没有提供"如何把收藏夹稳定地变成那个样子"的导出器**
- 对 offline 源标记 `originalFetched: true`，不尝试抓原文——这是对的
- 但缺少 RAG 层：只做"导入 + 展示"，没有"理解 + 检索"

**结论**：QMReader 的架构是对的（RSS 自动源 + localOnly 手动源），但它是一个"阅读器"，不是一个"知识索引系统"。

## 三、已有成熟方案（不需要从零造）

### 3.1 收藏夹同步：`social-favorites-to-obsidian` + `my-collection-skills`

**`social-favorites-to-obsidian`** 做的正是"收藏夹 → 本地 Markdown → Obsidian"：
- 增量抓取小红书和知乎收藏
- 导出为 Obsidian Markdown（frontmatter + 正文 + 图片本地化）
- CookieCloud 管理登录态
- 可生成 cron 定时任务

**`hc-tec/my-collection-skills`** 的抓取策略：
- API 优先，遇到签名/反爬则用 Playwright 加载真实浏览器读取 hydrated state
- 避免脆弱的 DOM 解析
- 明确"永远不依赖 RSSHub"
- 支持 offset/count 分批断点续导
- 卡片不足时增量滚动触发懒加载

**`rednote-mind-mcp`** 处理的关键问题：
- xsec_token 自动提取（收藏列表里的 URL 需要带上这个 token 才能访问笔记正文，否则 403/404）

**结论**：小红书收藏夹的"自动同步"已经有直接可用的实现。代价是接受"用真实浏览器驱动"而不是"纯 API 逆向"。

### 3.2 RAG 索引：`some-vault-some-mcp` / `Second Brain MCP`

**`some-vault-some-mcp`**（静态索引层）：
- 对 Obsidian vault 做混合检索（向量相似度 70% + 全文关键词 30%）
- LanceDB 本地存储 embedding
- 文件系统 watcher 做增量索引（2 秒 debounce，基于 mtime 检测变化）
- 以 MCP Server 形式暴露给任何兼容的 AI 客户端

**`Second Brain MCP`**（动态记忆层）：
- 增量索引（只重算变化的文件及其影响的图边）
- 额外构建 note-association graph：混合语义相似度、wikilink、共享标签和共现关系
- 可以问"什么和这条笔记相关，以及为什么"，而不是只做"文本匹配"
- 以 MCP 工具形式暴露给 Cursor、Claude Desktop 等

**结论**：不需要自己搭向量库。选一个 MCP Server 接入，把 vault 路径指过去，先让索引跑起来。

### 4.2 数据流

```
[浏览器插件 MarkDownload / SingleFile]
        │
        ▼  单篇临时保存
[Obsidian Vault / 指定目录]
        │
        │  social-favorites-to-obsidian (cron)
        ▼  收藏夹增量同步
[Obsidian Vault / 收藏夹目录]
        │
        │  手动写感想（[[原文]] 回链）
        ▼
[Obsidian Vault / 感想目录]
        │
        │  some-vault-some-mcp (watcher)
        ▼  增量索引
[LanceDB 本地向量库]
        │
        │  MCP 协议
        ▼
[AI 客户端 / Cursor / Claude Desktop]
```

### 4.3 感想沉淀的最小属性

不需要复杂的分类系统。只需要：

**frontmatter**：
```yaml
---
type: fragment  # fragment / book / method / log
tags: [AI, Agent]
source: "[[万有引力AI - Claude Code 实战]]"
created_at: 2026-10-21
---
```

**正文**：
```markdown
今天读到万有引力AI关于 Claude Code 的实战分享，核心观点是：
Agent 的价值不在于"自动完成任务"，而在于"把人类的思考过程外化"。

这和 Second Brain MCP 的 note-association graph 思路一致——
重要的不是单条笔记的内容，而是笔记之间的关系。

[[Second Brain MCP]]  [[Agent 设计模式]]
```

**关键原则**：
- 当天捕获时只写两三句，不整理
- 用 `[[原文]]` 双向链接，不复制粘贴原文内容
- 分类靠 `type` 字段 + Dataview 查询，不靠目录结构
- 系统越轻，越可能在捕获的那一刻真的写下感想

## 五、实现路线图

### Phase 1：跑通收藏夹同步（1-2 周）

**目标**：小红书收藏夹增量同步到 Obsidian

**步骤**：
1. 部署 `social-favorites-to-obsidian`
2. 配置 CookieCloud（或手动导出 Cookie）
3. 跑通一次全量导出
4. 配置 cron 定时任务（每天凌晨 3 点增量同步）
5. 验证增量逻辑：新增收藏 → 下次同步只抓新条目

**验收标准**：
- 收藏夹 500+ 条笔记全部导出为 markdown
- 图片本地化到 vault
- 增量同步只抓新增条目，不重复抓取

**放弃**：
- 放弃用 MediaCrawler 做这件事
- 放弃纯 API 逆向（接受 Playwright 驱动真实浏览器）

### Phase 2：接入 RAG 索引（1 周）

**目标**：vault 内容可被 AI 客户端语义搜索

**步骤**：
1. 选择 `some-vault-some-mcp` 或 `Second Brain MCP`
2. 配置 vault 路径
3. 启动 MCP Server
4. 在 Cursor / Claude Desktop 中配置 MCP 连接
5. 测试：问"关于 Agent 设计模式，我之前读过什么？"

**验收标准**：
- 新写入的 markdown 在 2 秒内被索引
- 语义搜索能找到相关笔记（不是精确关键词匹配）
- AI 客户端能调用索引回答问题

**不纠结**：
- 不纠结切分策略（先用默认）
- 不纠结 embedding 模型（先用默认的）
- 先让索引跑起来，再优化

### Phase 3：感想沉淀工作流（持续）

**目标**：阅读时随手写感想，不整理

**步骤**：
1. 在 Obsidian 中建立模板：`templates/感想.md`
2. 配置快捷键：`Cmd+T` 插入感想模板
3. 阅读时：打开原文笔记 → `Cmd+T` → 写两三句 → 保存
4. 每周用 Dataview 生成"本周感想"视图
5. 每月回顾：哪些感想值得展开成独立笔记

**验收标准**：
- 每天至少写一条感想（不整理，不分类）
- 感想通过 `[[原文]]` 链接到原文
- Dataview 能按 `type` / `tags` / `created_at` 查询

**关键**：
- 不追求"完美分类"
- 不追求"结构化整理"
- 捕获那一刻的两三句话，比事后整理的长篇大论更有价值

### Phase 4：QMReader 集成（可选，2 周）

**目标**：RSS 自动源 + 本地 markdown 统一阅读体验

**步骤**：
1. 部署 QMReader
2. 配置 RSS / RSSHub 源
3. 配置 `localOnly` 源指向 vault 中的收藏夹目录
4. 验证：RSS 文章 + 收藏夹笔记在同一个列表里展示
5. 可选：接入 QMReader 的 AI 伴读（文章上下文对话）

**验收标准**：
- RSS 文章自动抓取
- 收藏夹笔记在 QMReader 中可读
- AI 伴读能基于文章内容回答问题

**可选**：
- 如果 Obsidian 已经够用，这一步可以跳过
- QMReader 的价值在于"双语翻译 + 乔木风格改写"，如果不需要可以不用

## 七、最需要放下的执念

**不要试图找一个"既能自动同步所有平台、又能做 RAG、又能管理感想"的一体化阅读器。**

这个组合不存在，而且即使存在，它也会在某个平台改变防御策略时整体失效。

正确的做法是：
- **把"同步"交给专门的导出器**（`social-favorites-to-obsidian`）
- **把"索引"交给 MCP Server**（`some-vault-some-mcp` / `Second Brain MCP`）
- **把"感想"留给自己在 Obsidian 里写两三句话**

这三件事各自都有成熟方案，粘合成本远低于继续改造一个定位错配的爬虫，或等待一个不存在的完美阅读器。

## 八、技术选型总结

| 层次 | 工具 | 理由 |
|------|------|------|
| 收藏夹同步 | `social-favorites-to-obsidian` | 增量同步、Playwright 驱动、CookieCloud、cron 支持 |
| 存储格式 | Obsidian Markdown | 纯文本、双向链接、插件生态、长期可用 |
| RAG 索引 | `some-vault-some-mcp` 或 `Second Brain MCP` | 本地 embedding、watcher 增量索引、MCP 协议暴露 |
| 交互界面 | Obsidian + AI 客户端 | Obsidian 做浏览/写作，AI 客户端做问答/调用 |
| RSS 阅读（可选） | QMReader | 双语翻译、AI 改写、localOnly 模式 |

## 九、风险与应对

| 风险 | 概率 | 应对 |
|------|------|------|
| 小红书改变防御策略，Playwright 方案失效 | 中 | 降级为手动导出（浏览器插件 MarkDownload） |
| MCP Server 索引质量不够 | 低 | 调整混合检索权重（向量 vs 全文） |
| 感想沉淀坚持不下来 | 高 | 降低门槛：不整理、不分类、只写两三句 |
| Obsidian vault 越来越大，索引变慢 | 低 | LanceDB 支持增量索引，watcher 只处理变化文件 |
